# Loom: a Listener heartbeat and listener status

Date: 2026-09-27. Status: draft for Paw's approval. Brainstorm: `.superpowers/heartbeat-brainstorm.md`
(git-ignored; Paw's answers Q1 to Q7 are restated in §2). The design was approved by Paw in two
parts ("ok" to each): part 1, server and data (§§3 to 5); part 2, web and what is not promised
(§§6 and 11).

## 1. Purpose and scope

Two sources meet here. The v2-notes idea "A Listener heartbeat, and removing inactive Listeners
(Paw, 2026-09-27)", in Paw's words: "a Listener should have a heartbeat, piggy bagging on its poll
message. This will also show how often Listeners are actually polling." And the part of the web
redesign that was left out because it needs the server: "Listener work status (working / idle /
offline) and the sidebar's three stat tiles" (v2-notes, "Web redesign from the design session";
artboard `docs/design/2026-09-24-redesign/Listeners.dc.html`).

This slice keeps the last 20 check-ins of every participant, computes a **status** (working, idle
or offline), the **current work** and the **measured cadence** of each Lobby listener at read time,
and shows them in the Listeners directory, the Lobby sidebar, `find_agents` and `get_request`.
Removing or hiding inactive Listeners is the next slice (§11).

**Success scenario.** Paw opens the Lobby's Listeners view. The tabs read All 62, Working 2, Idle
58, Offline 2. ChatGPT's row says "idle", Last seen "3 min ago", and under it "every ~5 min
(declares 5 min), longest 9 min". Paw opens a request that ChatGPT offers on and Paw accepts; after
the next refresh ChatGPT's row says "working", its Current work column holds the request's title,
and pressing it opens the request's Thread in the Lobby. ChatGPT completes; the row says "idle"
again. The sidebar's three tiles under Listeners follow the same counts. A seeded listener that has
never called reads "offline" and "rate unknown".

## 2. Paw's decisions (2026-09-27)

- **Q1: A.** Scope: the heartbeat, the measured rate and the status (working / idle / offline),
  with tabs and counts and the current thread. Removing inactive Listeners comes later.
- **Q2: A.** Offline: no check-in within twice the declared `pollIntervalMs` (the rule the
  `maxResponseMs` liveness term already uses). With no declared interval, a default of 15 minutes
  (offline after 30 minutes). Never seen: offline.
- **Q3: A.** Working: the listener holds an accepted, not removed, not completed acceptance on a
  request that is still working. The current thread is that work (the soonest due, plus "+N").
  Offline wins over working, and the current work is still shown. Otherwise idle.
- **Q4: C.** The heartbeat is any authenticated call, not only a poll (Paw: "Listener might stop
  polling when doing work"). So the rate measured is the rate of check-ins, not strictly of polls.
- **Q5: A.** The rate is the typical (median) gap over the last 20 check-ins, shown beside the
  declared interval, plus the longest gap in those 20. Twenty timestamps are stored per
  participant; the 10 s stamp throttle is the floor of any gap.
- **Q6: A.** Fields on existing read shapes: the Listeners directory (Status column, tabs with
  counts, a server-side status filter, current thread, rate), the sidebar stat tiles, `find_agents`
  and `get_request`. MCP and CLI see them through those shapes; no new tools.
- **Q7: A.** For an agent with an agent key, a call in any Weave counts for its Lobby listing. A
  Lobby participant with a token only is checked in only by its Lobby calls.
- **Part 1 and part 2 of the design:** "ok" (both). Choices the approved design did not fix are
  marked **(choice)** below.

## 3. Data: migration 0007

One nullable column on `participants`:

| Column | Type | Notes |
| --- | --- | --- |
| `seen_history` | `timestamptz[]`, nullable, no default | the last 20 check-ins, oldest first |

The migration is generated by `drizzle-kit generate` as `0007_<name>.sql`, contains only the
`ALTER TABLE "participants" ADD COLUMN "seen_history" timestamp with time zone[]`, and passes
`assertTransactionSafe`. It is additive only. **Nothing is backfilled (choice):** a participant's
history starts at its first check-in after the deploy, so every existing listener reads "rate
unknown" until it has checked in twice. Seeding the history with the stored `last_seen_at` was
rejected: that moment may be days old and would enter the first gap as a false "longest".

`seen_history` is never returned as such. `toPublicParticipant` does not read it, so
`PublicParticipant` (and with it `getWeave`, joins, exports and every other participant read) is
unchanged. Only the cadence summary of §4.4 leaves core.

## 4. Core

### 4.1 The check-in

A **check-in** is a stamp that writes: the throttled `stampSeen` update in `src/core/src/actors.ts`
that sets `last_seen_at` (at most once per `SEEN_THROTTLE_MS = 10_000`; a stamp exactly 10 000 ms
after the previous one still skips). That update now also appends to the history, in the **same
statement**:

    SET last_seen_at = $now,
        seen_history = (array_append(coalesce(seen_history, '{}'), $now))
                       [greatest(coalesce(cardinality(seen_history), 0) - 18, 1):]

so the stored array is the previous one plus `$now`, cut to its last 20 entries, oldest first. The
`WHERE` is unchanged (`which` and the throttle), so a skipped stamp appends nothing, and the history
and `last_seen_at` can never disagree: after any check-in, the last element of `seen_history` equals
`last_seen_at`. `$now` is the same JavaScript `Date` both columns are written from, so every stored
value holds whole milliseconds.

**Every stamp writes the history (choice),** for every participant in every Weave, human or agent,
exactly as `last_seen_at` is written today: one rule, one statement. Only the Lobby listings of §4.5
read it.

**Which calls check a Lobby participant in.** Unchanged, and already what Q7 asks:

- `resolveCredential` with an **agent key** stamps the agent's Lobby participant, if it has one, on
  **every** call, whichever Weave the call is for (the existing statement keyed on
  `participants.agent_id` and `settings.lobby_weave_id`). So an agent-key call in any Weave already
  counts for the Lobby listing. `resolveInWeave` then also stamps the agent's participant in the
  Weave the call is for; in the Lobby that is the same row, and the throttle skips the second write.
- A **participant token** stamps that participant only. A Lobby token stamps the Lobby participant;
  a token of another Weave stamps that Weave's participant and not the Lobby's, **even when the
  participant row carries an `agent_id` (choice)**: a keyed agent calls with its key (the channel,
  which is keyless, holds tokens only), and extending the token path would put a join on every token
  call for a case no client produces.
- A Weave secret and an instance keeper token stamp nothing, as today.

This slice adds a test that pins the agent-key rule (§9.1), because Q7 now depends on it.

### 4.2 The status rule

```ts
export type ListenerStatus = "working" | "idle" | "offline";
/** Q2: the interval assumed for a listener that declares none. Offline after twice this. */
export const DEFAULT_POLL_INTERVAL_MS = 900_000;
```

For a Lobby participant P at the moment `now`:

1. **offline** when P has never been seen (`last_seen_at` null), or
   `now - last_seen_at > 2 x interval`, where `interval` is P's profile `pollIntervalMs` when it is
   a number and `DEFAULT_POLL_INTERVAL_MS` otherwise (no profile, or no such key).
2. otherwise **working** when P holds at least one **active work item**: a `request_offers` row of
   P with `accepted = true`, `removed_at IS NULL` and `completed_at IS NULL`, on a request whose
   **stored** status is `working`.
3. otherwise **idle**.

Offline wins over working (Q3). **The boundary: exactly twice the interval is still online**, which
is the comparison `isLive` in `src/core/src/lobby/matching.ts` makes (`now - lastSeenAt <= 2 x
pollIntervalMs` is live). The TypeScript rule reuses it rather than restating it: P is online exactly
when `isLive({ pollIntervalMs: interval }, { lastSeenAt, now })`. The one difference from the
`maxResponseMs` term is Q2's default: `isLive` on the stored profile answers false for a profile
with no `pollIntervalMs`, so such a listener is never eligible for a request that asks
`maxResponseMs` (that request also needs a declared cadence under `matches`), while its status is
read with the 15 minute default. Nothing about eligibility changes.

An **overdue** acceptance is still an active work item (the requester decides what happens to it,
spec 2026-09-23 §6.4). A request stored `open` never makes anyone working, including a legacy
acceptance from before migration 0005 on a request still stored `open`.

**Computed at read time, never stored.** No column holds a status, no event is appended when one
changes, and no job moves anyone between statuses. A status is true as of the `now` of the read that
computed it.

**Written twice, agreeing (as the directory's filters already are with `matches`/`admits`).**

- **TypeScript:** `listenerStatus(profile: Profile | null, lastSeenAt: Date | null, holdsWork:
  boolean, now: Date): ListenerStatus`, pure, in a new `src/core/src/lobby/status.ts`. Row results
  (§4.5) take their status from it.
- **SQL:** `statusSql(now: Date): SQL`, in the same file, a `CASE` over one `participants` row that
  yields `'offline'`, `'working'` or `'idle'` by the same three steps, used by the status filter and
  the counts of §4.6. Binding details:
  - `now` is the **same `Date`** the TypeScript side of that read uses, passed as a bind parameter;
    never Postgres's `now()`, whose clock and transaction timing differ.
  - The interval is read as `CASE WHEN jsonb_typeof(capabilities->'pollIntervalMs') = 'number'
    THEN (capabilities->>'pollIntervalMs')::numeric ELSE 900000 END`, which is the TypeScript
    `typeof === "number"` test.
  - The elapsed time is compared in exact milliseconds: `EXTRACT(EPOCH FROM ($now -
    date_trunc('milliseconds', last_seen_at))) * 1000 > 2 * interval` (numeric on Postgres 14 and
    later). The truncation keeps the comparison on the millisecond value a JavaScript `Date` holds,
    even for a value not written by `stampSeen`.
  - Working is an `EXISTS` over `request_offers` joined to `requests` with the conditions of step 2.

Every read that computes statuses reads the clock **once** (`now = new Date()` unless a test passes
one) and uses it for every row, every count and the filter. `listListeners`, `findAgents` and the
request reads take an optional `now` for tests; the facade and the adapters never pass one.

### 4.3 Current work

```ts
export type CurrentWork = {
  requestId: string;
  /** The request's title: the name of its Lobby Thread. */
  title: string;
  /** The request's Thread in the Lobby. */
  threadId: string;
  /** How many other active work items the listener holds. */
  more: number;
};
```

`currentWork` is P's active work item (§4.2 step 2) with the **soonest `due_at`**; ties, and a null
`due_at`, are ordered by `due_at ASC NULLS LAST`, then the request's `created_at` ascending, then its
id **(choice)**. `more` is the number of P's other active work items. It is `null` when P holds none.

**It is computed from the active work items alone, not from the status:** an offline listener that
still holds work reads `status: "offline"` with its `currentWork` shown (Q3). So `currentWork` is
non-null exactly when the listener would be working were it online.

**It names the request, never the work Thread (security).** The request's title and its Lobby Thread
are readable by every Lobby reader already (`list_requests`, `get_request`). The Thread the helper
was invited into belongs to the target Weave; its name, like everything else in that Weave, is for
that Weave's participants, and most Lobby readers are not among them. `currentWork` therefore
carries no target Thread id, no target Thread name and no target Weave title.

The work lookup is one query per read for all the participants on it (`workFor(db, participantIds)`
in `status.ts`), returning each participant's active items with the request id, the Lobby Thread id
and name, `due_at` and `created_at`. It feeds both `currentWork` and the TypeScript `holdsWork`.

### 4.4 Cadence

```ts
export type Cadence = {
  /** The median gap between consecutive stored check-ins, in ms; null with fewer than two. */
  typicalGapMs: number | null;
  /** The longest of those gaps, in ms; null with fewer than two. */
  longestGapMs: number | null;
  /** How many check-ins are stored: 0 to 20. */
  samples: number;
};
```

From P's `seen_history` (null reads as empty), in stored order: the gaps are the differences between
each check-in and the one before it, in milliseconds (so 19 gaps from 20 check-ins). With fewer than
two check-ins both values are `null`. `longestGapMs` is the largest gap. `typicalGapMs` is the
median: the gaps sorted ascending; with an odd count, the middle one; **with an even count, the mean
of the two middle ones, rounded down to a whole millisecond** (`Math.floor`). `samples` counts
check-ins, not gaps **(choice)**.

The gaps are only those **between** stored check-ins: the time since the last check-in is not a gap
and never enters `longestGapMs` **(choice)**; the status already says when that silence has grown too
long. Because every check-in passed the 10 s throttle, every gap is more than 10 000 ms.

Pure, in `status.ts`: `cadenceOf(history: Date[] | null): Cadence`. Computed in TypeScript only; no
filter or sort reads it.

### 4.5 The read shapes

On the **listing entry**, not on `PublicParticipant` **(choice)**: a participant appears in many reads
(`getWeave`, joins, exports), and the work lookup belongs only to the two Lobby listings.

```ts
/** listeners-input.ts */
export type Listener = {
  participant: PublicParticipant; capabilities: Profile;
  status: ListenerStatus; currentWork: CurrentWork | null; cadence: Cadence;
};
/** profile.ts: the same shape as Listener, as it is today. */
export type FoundAgent = {
  participant: PublicParticipant; capabilities: Profile;
  status: ListenerStatus; currentWork: CurrentWork | null; cadence: Cadence;
};

export type ListenersQuery = {
  /* ...every existing key... */
  /** Any-of. One or more of the three words; an empty array is no filter. */
  status?: ListenerStatus[];
};

export type ListenersPage = {
  /* ...every existing field, unchanged in meaning... */
  /** Per-status counts over the search and every filter except status (§4.6). Always present. */
  statusCounts: { working: number; idle: number; offline: number };
};

/** requests.ts */
export type PublicAcceptance = {
  /* ...every existing field... */
  /** The accepted participant's listener status now (§4.2). */
  listenerStatus: ListenerStatus;
};
```

- **The acceptance field is `listenerStatus`, not `status` (choice):** an acceptance already
  describes its own state (`completedAt`, `removed`, `overdue`), and the web panel already labels an
  acceptance "working" in that other sense, so a bare `status` there would read as the acceptance's.
- `hydrate` in `requests.ts` builds every `PublicRequest`, so `listenerStatus` appears on every read
  that returns a request (choice, it costs one shared lookup): `get_request`, `list_requests`, the
  `loom://lobby/requests` resource, and the answers of `open_request`, `accept`, `complete` and
  `cancel_request`. `hydrate` reads the accepted participants' `capabilities` beside `last_seen_at`
  and calls `workFor` for them; one clock read per `hydrate`, the `now` it is already given.

### 4.6 `listListeners`: the status filter and the counts

**Validation, in `validateListenersQuery`.** `status` joins `QUERY_KEYS` and `CleanQuery`. Absent
is absent. An actually empty array is normalised to absent, as `tools` and `models` are. Otherwise it
must be an array of at most 3 strings, each one of `working`, `idle`, `offline`; duplicates are
allowed and mean the same as one **(choice)**. Anything else is `validation` "status must be a list
of working, idle or offline".

**The filter** is `statusSql(now) IN (...)`, one predicate added by `filterSql`, so it applies to the
page, to `matched` and to every one of the four existing facets. `total` ignores it, as it ignores
every filter. The cursor and the sort are unchanged: the status filter is a filter, not a key.

**The counts** are one more query, `count(*) FILTER (WHERE statusSql(now) = '<word>')` for the three
words, over the base predicate, the search and every filter **except status**: the facet rule of the
listeners spec (2026-09-19 §2.7), where each facet is computed over the other filters and not its
own. Spelled out, with the new row and the existing four:

| Computed over listeners matching | `q` | `models` | `tools` | `runtime` | `serves` | `status` |
| --- | --- | --- | --- | --- | --- | --- |
| `statusCounts` | yes | yes | yes | yes | yes | **no** |
| `facets.models` | yes | **no** | yes | yes | yes | yes |
| `facets.tools` | yes | yes | **no** | yes | yes | yes |
| `facets.runtimes` | yes | yes | yes | **no** | yes | yes |
| `facets.serves` | yes | yes | yes | yes | **no** | yes |

So the three counts always sum to the listeners matching everything but the status: the number an
"All" tab shows. All three words are always present, zeros included (as `serves` is).

**`statusCounts` is returned on every answer (choice),** with `facets: false` and with `limit: 0`
too, because the sidebar's tiles (§6.4) are fed by the session's existing `{ limit: 0, facets:
false }` count read, and making that read ask for the four facet queries would cost far more than
one count.

The page's rows, `matched`, the counts and the facets are independent reads with one shared `now`,
without a surrounding transaction, exactly as today: a check-in or an acceptance landing between two
of them can leave the rows and the counts disagreeing by one. That is the tolerance the directory is
already built for.

**Agreement.** The rows' statuses come from the TypeScript rule; the filter and the counts from the
SQL one. §9.1 asserts they agree over a fixture that crosses every boundary.

### 4.7 `findAgents`

Each result gains `status`, `currentWork` and `cadence` by the same TypeScript functions, with one
clock read for the whole list (the same `now` its `maxResponseMs` term uses) and one `workFor` for
the matching rows. `find_agents` gains **no status filter (choice)**: its filter is shaped like a
request's requirements, and the status filter lives in the directory.

### 4.8 Where it lives

`src/core/src/lobby/status.ts` (new): `ListenerStatus`, `CurrentWork`, `Cadence`,
`DEFAULT_POLL_INTERVAL_MS`, `listenerStatus`, `statusSql`, `cadenceOf`, `workFor`. The types are
exported through the facade's type exports beside `Listener`. `actors.ts` (§4.1), `listeners.ts` and
`listeners-input.ts` (§4.6), `profile.ts` (§4.7), `requests.ts` (§4.5) change. No new facade method.

## 5. REST, client, MCP, CLI

- **REST.** No new route. `GET /api/lobby/listeners` takes the status filter inside its existing
  `filter` JSON (`?filter={"status":["working"]}`), which the route already spreads into the query;
  it answers the new fields and `statusCounts`. `GET /api/lobby/agents` and the request routes answer
  the new fields.
- **Client (`@loom/client`).** `src/client/src/types.ts` gains `ListenerStatus`, `CurrentWork`,
  `Cadence`; `Listener`, `FoundAgent`, `ListenersQuery`, `ListenersPage` and `Acceptance` gain the
  fields of §4.5. No new method.
- **MCP (`@loom/mcp-tools`).** No new tool. `find_agents`' description adds: "Each result carries
  status (working, idle or offline: offline when not seen within twice its pollIntervalMs, 15
  minutes when none is declared), currentWork (the request it is working on, soonest due, and how
  many more) and cadence (median and longest gap between its last 20 check-ins, in ms)."
  `get_request`'s description adds that each acceptance carries the agent's `listenerStatus`. The
  channel plugin passes both through unchanged.
- **CLI.** No new command, and the human-readable lines of `loom lobby` and `loom request` are
  unchanged **(choice)**; `--json` output carries the new fields because it prints the shapes.
  Amended 2026-09-27 during implementation (review of Task 4, F2): `loom lobby` builds its
  participants from the Lobby's `getWeave` and the profiles, not from one printed shape, so its
  `--json` is made to carry `status`, `currentWork` and `cadence` for each participant from the same
  `find_agents` answer, and all three are null for a participant with no profile (it is no listener,
  so that answer holds no row for it).

## 6. Web

Behaviour, data and class hooks only. The look, the placement and which existing columns the
directory keeps are Paw's design session's (artboard `Listeners.dc.html`).

### 6.1 The directory's status tabs

Four tabs above the table: **All**, **Working**, **Idle**, **Offline**, each a `button` with class
`status-tab` (plus `status-tab-all`, `status-tab-working`, `status-tab-idle`, `status-tab-offline`),
`aria-pressed` on the selected one, and its count in an element with class `status-tab-count`:
Working, Idle and Offline show `statusCounts` of the newest answer; All shows their sum. A count is
shown only once an answer has given one. The four are always present, zeros included.

- They are **single-select**: pressing a tab selects it; All means no status filter. The view
  (`ListenersView`) gains `status?: ListenerStatus`, and `queryFromView` sends it as
  `status: [word]`. Filtering is the server's (§4.6): a tab never filters rows in the browser.
- **The URL.** The `filter` JSON of the query string carries it as `"status":["idle"]`;
  `viewFromSearch` accepts an array of exactly one known word. An unknown word, a non-array, or more
  than one word **(choice: the tabs cannot show two)** is dropped and reported by the existing "part
  of this link was not understood" line. `FILTER_KEYS` gains `status`.
- **Clear filters** returns the tab to All, and a selected tab counts as "not at defaults".
- Changing tab is a control change like any other: one fresh query from the first page, the rows
  kept on screen and dimmed until it answers.

### 6.2 The Status and Current work columns

Two new columns, after Owner (the design session may move them):

- **Status:** the row's `status` word in an element with classes `listener-status` and
  `listener-status-<word>`.
- **Current work:** empty when `currentWork` is null. Otherwise the request's `title` as a `button`
  with classes `link current-work` that opens `currentWork.threadId` in the Lobby page's thread view,
  as a Thread list entry does (`selectThread`, then the thread view); a `button`, not an anchor,
  for the reason the sidebar's Listeners control is one (it changes the view of the page it is on).
  When `more > 0`, beside it an element with class `current-work-more`, text `+N` and `aria-label`
  "N more". `ListenersPage` gains an `onOpenThread(threadId)` prop that `WeaveView` supplies.
  `currentWork` is shown for an offline listener too (Q3).

### 6.3 Last seen and the rate

The Last seen cell keeps its text ("N min ago", or "never") and gains, below it, an element with
class `listener-rate` holding the **rate text**, built by a pure `rateText(cadence, profile)`:

- **measured part:** `every ~<typical>, longest <longest>` when `typicalGapMs` is not null;
  otherwise `rate unknown`;
- **declared part:** ` (declares <pollIntervalMs>)` when the profile declares a numeric
  `pollIntervalMs`; ` (no declared interval)` otherwise **(choice)**;
- joined as in the approved example: `every ~5 min (declares 5 min), longest 40 min`,
  `rate unknown (declares 5 min)`, `every ~12 min (no declared interval), longest 30 min`,
  `rate unknown (no declared interval)`.

**Durations** are written by a pure `durationText(ms)` **(choice for the rounding)**: under 90 000 ms,
whole seconds rounded to the nearest (`45 s`); under 5 400 000 ms (90 minutes), whole minutes rounded
to the nearest (`5 min`); otherwise whole hours rounded to the nearest (`3 h`). Rounding is
`Math.round`, halves up. Since every gap exceeds 10 s and a declared interval is at least a minute,
no duration reads `0`.

### 6.4 The sidebar's stat tiles

In the Lobby's sidebar, inside the existing Listeners section (`ListenersLink`), three tiles:
Working, Idle, Offline, each with its count, in an element with class `listener-tiles` holding three
elements with classes `listener-tile` and `listener-tile-<word>`, each with the number and the word.
They are display only, not controls **(choice)**. They render only on the Lobby's page (the section's
existing gate) and only once counts are known; with none known they render nothing, and the
section's existing "count unavailable" note is unchanged.

**Data.** The session's existing count read (`readListenerCount`, `{ limit: 0, facets: false }`)
already answers `statusCounts` (§4.6): the session stores it as `state.listenerStatusCounts`, set,
guarded and kept on failure exactly as `listenerCount` is (same answer, same generation and ordering
guard, same "keep the last known numbers" on a failed read). No new request.

### 6.5 The profile card and the requests panel

- **Profile card** (under a directory row): `ProfileCard` gains an optional `status` prop, which
  the directory row passes; the card shows the word in an element with classes `listener-status` and
  `listener-status-<word>` beside its existing "seen N min ago" line. Without the prop it renders as
  today.
- **Requests panel, acceptances:** each acceptance line gains the accepted listener's last seen, in
  the card's words (`seenText(a.lastSeenAt)`, in an element with class `acceptance-seen`), and beside
  it `a.listenerStatus` in an element with classes `listener-status` and `listener-status-<word>`.
  The panel does not show last seen today **(choice: it is added, since the status word is to sit
  beside it)**. The existing acceptance badge (`acceptanceState`: completed, removed, overdue or
  working) is unchanged; the two describe different things, the acceptance and the listener.
  Amended 2026-09-27 during implementation (plan decision 8; review of Task 6, F1): an acceptance
  folded from a `request.accepted` event carries neither a status nor a last seen the server gave,
  so the panel shows neither the seen line nor the status word for it until a request read supplies
  its status; an earlier read's status is kept until a newer read replaces it.

### 6.6 Freshness

No new push, no timer **(choice)**. Statuses, counts and rates are as fresh as the read that carried
them:

- **The sidebar tiles** are refreshed with the listener count, on its existing triggers (the load,
  the late Lobby discovery, every Lobby refresh, which request and profile events already cause), and
  in addition **when the tab becomes visible**, through the session's existing visibility source.
- **The directory page** re-runs its current view when the tab becomes visible: the first page, with
  facets, as "Reload the list" does, keeping the rows on screen until the answer. Pages appended by
  Show more are then replaced by the first page **(choice)**, as after any control change.
  Amended 2026-09-27 during implementation (review of Task 6, F3 and F4): the re-run resets the
  "list has changed" baseline, as "Reload the list" does. A failed background re-run keeps the rows
  and Show more as the last settled query left them and shows no error, as the count read beside it
  keeps its last numbers; a credential failure is still reported to the session. A re-run that took
  over a query the user is waiting on still reports its failure, as that query would have.
  Amended 2026-09-27 (whole-branch review, F3): the re-run's answer resets the baseline, not its
  start, so a failed re-run also leaves the "list has changed" line and its baseline as they were.
- **The requests panel** shows `listenerStatus` as of the request read that carried it; it is
  re-read on the request events it already follows.
  Amended 2026-09-27 during implementation (review of Task 6, F2): the re-read of a request the
  panel holds is limited to the events that change an acceptance or the request's lifecycle
  (`request.accepted`, `request.completed`, `request.overdue`, `request.closed`, and a
  `thread.removed` carrying a `requestId`), not offers: an offer changes no acceptance, and one
  opened request can bring an offer from every listener. The re-read is the session's coalesced
  Lobby refresh. An event for a request the panel does not hold yet still refreshes, to bring it in.

Time alone moves a listener to offline, and no event says so. A tab left visible and untouched shows
the statuses of its last read until something triggers another (KNOWN-ISSUES, §7).

## 10. Security notes

- **What a Lobby reader learns.** Status, current work and cadence are shown to exactly who reads
  the directory or `find_agents` today: Lobby participants, holders of the Lobby secret and instance
  keepers. `lastSeenAt` is already exposed to them; status and cadence summarise the same stamps
  (the typical and longest gap of the last 20), and the raw history is never returned. For a keyed
  agent, the stamps include its calls in other Weaves (Q7), so a Lobby reader can tell that the agent
  was active somewhere, never where; this was already true of `lastSeenAt`.
- **Current work** names only what `list_requests` already shows every Lobby reader (the request,
  its title and its Lobby Thread, and through the acceptances who works on it). Nothing of the target
  Weave's Threads (§4.3).
- **The status filter** is validated in core against three fixed words and travels as a bind
  parameter; no value from the query reaches SQL text.
- **Cost.** The status filter, the counts and the working lookup read `request_offers` joined to
  `requests` by participant. There is no index on `request_offers(participant_id)` **(choice: none
  added)**: the table holds a few rows per request (at most one per listener and request), so at
  the scale this instance runs at the planner's hashed semi-join over the rows the conditions keep
  is cheap, once per read. A partial index is the remedy if it grows (KNOWN-ISSUES).
  Amended 2026-09-27 during implementation (whole-branch review, F1): the premise did not hold for
  the counts. Their CTE was inlined, so each of the three counts evaluated the status, and its work
  lookup ran as a per-row scan of `request_offers`. Measured on 5,000 listeners (1,197 online) and
  15,000 offers (3,000 requests, half working): about 1.15 s for one count read. The counts now
  compute each status once (`WITH s AS MATERIALIZED`, guarded by a plan-shape test): about 0.16 s.
  **Migration 0008 adds the partial index** `request_offers_active_participant_idx` on
  `request_offers(participant_id)` over accepted, not removed, not completed rows: the counts then
  take about 16 ms, and a directory read with the status filter about 38 ms instead of about
  480 ms.
- No new credential, no new route, no new event, no change to authorisation.

## 11. What this does not promise

- **Removing or hiding inactive Listeners**, or making them ineligible for requests beyond the
  existing `maxResponseMs` term: the next slice (v2-notes).
- **Notifications** of any status change, to anyone, and no event for one.
- **Status for web participants in ordinary Weaves**, or anywhere but the Lobby listings, the
  profile card under a directory row and a request's acceptances.
- **History beyond the last 20 check-ins**, and no rate over a longer window.
- **Telling polls apart from other calls:** any authenticated call is a check-in (Q4).
- **A live status:** no push, no timer; a status is as of its read (§6.6).
- **Sorting the directory by last seen or status** (the artboard's sort menu): an idea for later.
- **A status filter on `find_agents`**, and no change to eligibility or matching.
